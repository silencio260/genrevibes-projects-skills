# App icon concepts

Inspect the app category, current icon, user references, and explicit feedback.
Existing files are useful references; their presence does not prove approval,
and a missing file does not prove rejection.

- Follow the requested style and quantity. If unspecified, create a small set
  of distinct concepts rather than ten near-duplicates.
- Use one recognizable subject, a clear silhouette, and enough contrast to
  remain readable at launcher size. Avoid tiny text and unnecessary detail.
- Use bitmap generation/editing tools for requested raster concepts. Preserve
  an existing vector workflow when the user asks to edit vector artwork.
- Use the app's brand when requested. Avoid adding unrelated logos or copying
  another app's identity.
- Save variants under `app promotional assets/app-icon-concepts/<campaign>`
  unless another destination was supplied. Keep source concepts separate from
  platform exports and preserve existing work.
- For a multi-image set, provide and inspect a contact sheet. Inspect individual
  finals at small size for clipping, garbled details, and accidental duplicates.

Use [promotion style references](../app-promotions/references/styles.md) only
when relevant to the requested look; launcher presets are not universal defaults.
Record explicit rejection notes before another iteration. Do not invent feedback.

Report output files and whether they are concepts or platform-ready exports.
Apply the selected asset through [branding](../branding/SKILL.md) when requested;
do not replace the live app icon merely because concepts were generated.

## Turn the brief into inspectable concepts

First identify the subject, required brand elements, desired style, and how much
variation the user requested. Read existing reference images before describing
them. If the user rejected a previous direction, keep the actual reason in the
iteration notes; do not infer rejection from an unused file.

Make alternatives differ in an intentional way, such as silhouette, composition,
or treatment. Label their source files clearly and retain the originals. A
contact sheet helps compare the set, but inspect selected images individually
at small launcher size as well as full size.

Check the actual output for accidental lettering, muddy edges, extra objects,
and loss of the subject under common launcher masks. If the user asked for a
transparent asset, inspect transparency rather than accepting a checkerboard
painted into the image.

Deliver the concept files and a clear distinction between an approved source
and platform resources. Once a source is selected and applying it is requested,
use the branding skill to derive the correct layers/exports. Do not stretch one
flattened concept into every platform resource without checking the result.
